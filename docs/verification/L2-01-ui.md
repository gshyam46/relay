# L2-01 React context verification

Date: 2026-09-12. Product: **AI Lead Intelligence & Outbound Automation**.
Scope: local implementation of the [recorded business-context contract](../L2-01_BUSINESS_CONTEXT.md). This is automated browser and engineer visual evidence with synthetic data, not customer/operator acceptance or a live PostgreSQL/provider check.

## Completed

Settings opens the Business profile view with business name, offerings, service areas, target customers, exclusions, fit criteria, preferred next step, timezone and language. Optional missing values stay unknown. Criteria are described as recorded human input; the UI does not promise business-fit scoring or sending-hour enforcement.

Lead detail has a deep-linked Enquiry view for six typed facts, per-value source/assertion/time, exact monetary strings, UNKNOWN and 2-5 conflicting alternatives. New budget entry requires selecting the stated currency. Resolving a conflict requires entering a reviewed value and source; the first alternative is not silently selected. Revision history preserves prior values and reasons, including exact amounts after a fact is cleared.

Owner forms load saved state before initialization, retain unsaved drafts through background refresh and validation/conflict errors, require a save reason, and explicitly confirm before replacing a draft with the saved revision. Other authenticated users receive read-only context. Domain authorization and validation remain server-enforced. Context saves invalidate the actual React Query keys for lead details, intelligence summaries/history, actions, attention, timeline and activity; a cached summary cannot continue treating the prior context as current.

Settings navigation is horizontal below the existing desktop breakpoint and the new forms use bounded responsive grids. Broader application-shell mobile navigation is unchanged. The nearby manual-message success text now directs the operator to review the exact recipient/message rather than promising an automatic send.

## Defects found and corrected during verification

New textarea/select labels initially included changing field/helper text in their accessible name. Explicit matching accessible names now keep labels stable, including when a validation error retains a non-empty reason. This was verified by continuing to correct and save the same draft.

Independent integration review found a wrong intelligence cache key. The correct intelligence-summary and affected detail/activity keys are now invalidated; check 15 proves the visible behavior.

The preserved conflicting-enquiry browser scenario exposed a backend signal-grounding failure: metadata-only review evidence was incorrectly included in unrelated contact/readiness signal references. The integrating owner corrected those evidence inputs while preserving strict grounding validation. The same fixture then completed analysis and the summary-cache regression. The browser test was not changed to remove the conflicting enquiry.

Visual review found the source-time example accepted an explicit offset while the original backend input validator required canonical UTC. The backend owner aligned strict input normalization with the documented example; the final 16/16 browser rerun includes offset-to-UTC persistence/reload and a separate unknown time. Impossible dates and missing offsets remain rejected in backend tests.

Final synthetic desktop screenshots were captured in an owned OS temporary directory and inspected by an engineer agent: business-profile.png and enquiry-context.png. Text, form alignment, unknown/source distinctions and the full large decimal amounts were legible at 1440x1000. Screenshots contain only generated fixtures and are not committed as customer evidence.

## Known limits and human QA

The explicit installed Playwright module is not a new portable, dependency-locked CI browser setup. Full automated accessibility, browser/device coverage and application-shell mobile navigation remain future work. The existing large initial bundle remains a performance issue.

Required human acceptance remains open: a target operator configures their real offering and recognizes enquiry sources; understands recorded versus inferred/conflicted/unknown data; corrects a fact, refreshes intelligence and re-reviews affected sends; checks screen reader, keyboard, mobile/zoom, long multilingual values and stale-session recovery. Business calendars, import mapping/correction, reviewed duplicate resolution, company/person modeling and actual customer-fit ranking are not completed by this context UI. PostgreSQL, provider and pilot evidence remain separate gates.

Next implementation slice: reviewed CSV mapping and typed source linkage under L2-02, while keeping L2-01 operator and external acceptance open.
