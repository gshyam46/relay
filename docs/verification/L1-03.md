## Completed

- Added distinct transaction clients with lifetime/context enforcement, nested/parent-escape rejection, rollback integrity and no automatic business callback replay. SQLite serializes shared-connection work and asynchronously waits for a bounded write reservation; PostgreSQL pins one connection and retires unusable/ambiguous connections.
- Added createUnitOfWork and scoped approval composition. Request/current/approve/reject serialize on the tenant-owned action. Edited payload, approval, action state and audit commit or roll back together. Conflicting decisions produce one winner; same-decision retries preserve the existing result.
- Closed a legacy compatibility hole identified during review: new pending reviews and pending decisions require AWAITING_APPROVAL. Completed, executing, blocked and other non-reviewable states cannot be reactivated through approval. Repeating an already approved decision preserves later execution state.
- Kept 0001_baseline_schema unchanged. Added 0002_runtime_column_reconciliation, lock-before-history migration execution, migration/marker atomicity and fail-closed history checks. Unknown legacy authorization is quarantined or refused before permissive baseline adoption.
- Separated runtime opening and read-only status/readiness/deployment verification from explicit migration mutation. Startup refuses missing/pending/incompatible schema before listening; only the validated disposable memory E2E harness bootstraps at startup.
- Deployed migration commands require a dedicated job-only MIGRATION_DATABASE_URL. Render pre-deploy verifies using runtime credentials; its worker interval is disabled pending execution gates. No job, cloud role or secret was provisioned.
- Added safe database failure categories to boot/CLI/readiness and redacted pooled error logging.
- Added the requested [interactive landing specification](../LANDING_PAGE.md) and L4-07/L5-07 roadmap tasks, with public publication under L6-04. No landing frontend, public routes or commercial endpoint was implemented in this slice.

## Contracts changed

See the [implementation contract](../L1-03_PERSISTENCE.md), recorded before dependent composition changes.

- db.transaction(work, { lockTimeoutMs }) supplies a distinct transactionBound client; scopes cannot escape, nest, close the parent or silently use parent repositories.
- createUnitOfWork(db, buildContext).run(work) builds fresh scoped dependencies.
- ActionsRepository.getActionForUpdate(id, organizationId) requires a scoped transaction. PostgreSQL FOR UPDATE remains inside the repository.
- Approval HTTP payloads remain compatible. A new decision for a non-reviewable action now returns 409 instead of resetting its lifecycle.
- getMigrationStatus remains read-only and adds initialized, compatible, unknown and outOfOrder. Unknown/newer IDs or a gap are incompatible even when pending is empty.
- Readiness includes initialized/compatible and returns 503/schema_incompatible for incompatible history. Runtime openDatabaseClient options and openRuntimeDatabase prevent automatic schema adoption.
- loadMigrationConfig and MIGRATION_DATABASE_* variables separate deployed mutation credentials from runtime configuration.
- Normal local initialization now explicitly runs npm run db:migrate before npm start.

## Known issues and acceptance limits

- Real PostgreSQL concurrent approval/migration tests, failure recovery and restricted-role startup/inspection remain required. A read-only PostgreSQL session fixture, even when run, does not prove deployed grants.
- The forward repair supports its explicit synthetic previous-schema fixture. It does not repair arbitrary corrupt schemas or prove the shape of a real older deployment. Inventory an isolated restored release and record explicit legacy remediation first.
- Unknown newer migration history fails closed. Reverting to an older strict runtime may require a compatibility patch or roll-forward; an additive schema alone does not guarantee that older startup accepts it.
- Atomic approval is not immutable recipient/sender/content authorization. Actions can still require shared send-time policy, suppression and durable dispatch work.
- Action creation plus review request, import row/lead/event persistence, attempts and inbox effects have not all adopted a unit of work. L1-04 through L1-08 and L2-02 retain their documented scope.
- Database TLS identity verification and exact monetary/numeric contracts remain open. Disabling a blueprint interval worker is not a send kill switch and does not fix API/worker races or shutdown draining.
- Human task completion, inbox reply workflow, real-channel demonstration and customer value validation remain outstanding.
