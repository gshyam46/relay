Date: 2026-09-12. Local implementation under [L2-05](../L2-05_FRESHNESS.md) and ADR-017 in [DECISIONS](../DECISIONS.md). Implementation and automated verification are complete locally; required operator/external acceptance remains open. This is not launch certification.

## Completed

- Analysis distinguishes never analysed, current, outdated and archived. Current analysis can still report unknown, inferred, conflicting or aged facts. Explicit refresh reassesses saved sources without changing observation dates.
- Policy 1 applies a provisional 90-day observation-based TTL to ongoing enquiry facts and research. Historical dates retain their separate meaning. Missing, malformed, future-at-recording and conflicted evidence stay visible without acquiring current factual authority.
- Additive migration 0013 persists bounded snapshot assessments and a workspace time high-water. Neutral identity-only legacy fingerprints remain compatible; affected historical analysis needs explicit refresh. Full profile revisions continue to govern criteria changes.
- Direct generation and cached reuse recheck source/freshness and exact parent inputs outside/inside the correct transaction boundary. Expired approval cannot authorise dispatch. Actual already-authorised delivery remains recorded, without obsolete automatic follow-ups.
- API detail reads use one captured assessment instant in one workspace transaction, keeping the badge and dependent artifacts consistent across an expiry boundary. The UI explains source issues, previous/current recommendations and changed inputs without claiming model causation.
- Bulk refresh gives truthful per-lead success/reuse/failure, safe failure messages and retained failed/unprocessed selection. Historical metadata-only evidence renders as a review note rather than pretending to be a claim.

## Contracts Changed

- Currentness and freshness are additive API fields. Existing execution/readiness statuses remain separate.
- Detail includes at most two bounded stored recommendation descriptors and input-change categories. This is a comparison, not an explanation of model causality.
- Bulk selection accepts at most 1000 valid IDs, deduplicates, and processes at most 50 per request; results retain COMPLETED/FAILED plus reuse, currentness and safe codes. Existing plan-to-pending-action creation is preserved; refresh does not dispatch a provider.
- Snapshot assessment JSON is bounded to 256 KiB; research to 100 records/512 KiB with field limits; first-source history lookup to 1000 revisions/8 MiB.
- Currentness reads may advance only the technical time high-water. Ordinary domain rejection rolls back business work through a savepoint while retaining the validated time observation. A poisoned SQL transaction or storage/commit failure remains a failure and rolls back; this mechanism is not durability through unavailable storage.
- Source-time semantics, future historical dates, compatibility and exact ownership are in the [contract](../L2-05_FRESHNESS.md).

## Known Issues

The 90-day TTL is provisional. Research/history limits fail closed when exceeded; they are operating limits, not a measured scaling claim. Earlier adoption or a future policy version requires explicit contract/migration evaluation; no user-editable TTL control is introduced.

Actual PostgreSQL locking, savepoints, upgrade/restore and host-clock behavior remain unverified in this environment. Provider recovery, customer outcome quality, mobile/accessibility and the complete operator loop retain their launch gates. Local implementation is not pilot approval.
