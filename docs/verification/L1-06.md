Product: **AI Lead Intelligence & Outbound Automation**.
Date: **2026-09-11**.
Status: local implementation and automated verification for this bounded slice; **L1 remains in progress**. No deployment, customer database migration or real provider send was performed.

## Completed

The [contract](../L1-06_SCHEDULING.md) was recorded before dependent implementation. ADR-012 in [Decisions](../DECISIONS.md) uses the existing modular monolith, PostgreSQL direction and workspace transaction gate.

- Immutable migration 0007 adds managed domain-event input identity, retry budgets, leases/fences, processing stages/reviews, scheduler cursors/visit leases, and explicit workflow/action linkage. Existing 0001-0006 migrations are unchanged by this slice. Legacy domain events and ambiguous workflow/action history remain held; no old execution authority is inferred.
- The normal server now gives up to four distinct eligible workspaces a bounded turn, with persisted workspace and phase rotation. Receipt, lead-event, workflow, follow-up, dispatch and lease-expiry phases have separate caps. A slow tenant or phase cannot repeatedly occupy every admission slot. A 10-second soft admission budget stops new work; admitted operations retain their own timeout/lease limits.
- Managed domain events have five attempts, a 24-hour deadline from first claim, 120-second fenced leases and persisted exponential retry timing with jitter. A fixed own-property handler registry supports LeadCreated, LeadReplyReceived and ActionCompleted; unsupported or ambiguous events are visible review work. Owner decisions retain original input and retry budgets.
- Initial lead processing atomically normalizes eligible input, stores intelligence, plans at most one initial action and records audits/cursors. Durable contact restrictions across duplicate identities prevent new contact planning; pending mandatory receipt policy defers it.
- Reply processing stores the deterministic snapshot and prepares exact typed stage input under a short workspace transaction. Synthesis/recommendation/planning generation occurs outside database transactions, then the validated artifact, supersession, audit and stage cursor commit together only if the current input and event fence/lease still match. Current ready artifacts are reused. Generation is capped at 30 seconds per stage; a crash after generation can repeat a bounded model call and is not an exactly-once cost guarantee.
- Restricted contacts still receive an updated reply snapshot, with contact-recommendation stages explicitly skipped. Opt-out during generation prevents stale output from committing. Event failures store fixed safe codes, with ownership rechecked after gate wait and after the final write; expired owners cannot overwrite replacement work.
- Workflow advancement is DB-only. A send step creates one action requiring exact human review, then waits for the exact execution to deliver and complete. Approval, provider acceptance, retry and uncertainty cannot advance a step. Waits and subsequent delays use persisted timing anchors across overdue ticks/restart.
- Owners can create a basic campaign/sequence, enroll with a start time, inspect current work, review the exact action and pause/resume/stop at the displayed revision in Workflows. Dispatch checks current run, step, lead, parent state and linkage under the action gate. Paused work consumes no attempt; stopped/invalid work cannot dispatch. Requests already authorized before a stop may still finish.
- Every canonical inbound reply stops its existing sequence, including questions and uncertain replies, while preserving the appropriate human-response task. A stop survives a later message/outbox failure. New stop_on_reply=false inputs are rejected because continuing after a reply is unsupported; historical false settings remain conservative. This stop does not invent contact suppression or change the lead lifecycle.
- Scheduled follow-up records become DUE once with an audit. Invalid/missing historical due times become BLOCKED review work. Activity shows Scheduled, Due and Needs review accurately. Completion accepts only PLANNED/DUE; cancellation accepts PLANNED/DUE/BLOCKED. Exact repeats are idempotent and conflicting terminal transitions return 409; state and audit commit together. Completing a follow-up record does not complete a linked workflow human-task action.
- Owner Event recovery now separates Lead processing from received webhooks. It shows safe stages, timing, attempts and review history; exact-fence retry/close decisions cannot expose raw payload, edit input, reset budgets, promote legacy history or dismiss mandatory webhook policy.

## Contracts changed

- GET /api/domain-events and GET /api/domain-events/:id are owner-scoped and return safe state/stage/review data. List accepts state/limit/offset. POST /api/domain-events/:id/review accepts expected_fence, decision RETRY/CLOSE and evidence_note, deriving workspace/actor from the session.
- POST /api/workflow-runs/:id/control accepts expected_revision, command PAUSE/RESUME/STOP and reason, using session workspace/actor. Enrollment accepts scheduled_at as a valid UTC instant. Invalid new stop_on_reply=false sequence/step inputs are rejected.
- Workflow runs now distinguish scheduled work, waiting for review, waiting for actual execution, pause, stop and blocked history. Exact linkage, current revision, delivery facts and persisted anchors govern transitions.
- Follow-up complete/cancel retain the existing response shape {follow_up, duplicate}. Invalid or conflicting terminal transitions return FOLLOW_UP_STATE_CONFLICT (409); wrong-tenant/missing rows remain generic 404.
- Worker.runOnce returns bounded visits and per-phase outcomes plus compatible aggregate arrays. A scoped developer run performs one bounded workspace visit; it no longer promises to drain all pending events. Normal scheduling needs no developer control.
- Schema 0007 is required before runtime startup. Deploy it through the existing explicit migration job and validate against a disposable PostgreSQL target before a customer upgrade.

## Known issues and limits

- Local SQLite checks and compilation do not establish real PostgreSQL multi-process claims, index/load behavior, least-privilege migration/runtime roles, backup/restore or managed-host readiness. PostgreSQL-gated tests remain skipped locally.
- No live provider send, signed provider redelivery, customer data, production migration or deployment was used. Provider acceptance is distinct from delivery and a completed message is distinct from a business outcome.
- No browser runner or human walkthrough was completed. Keyboard/mobile/focus, schedule/timezone clarity, stale review handling and end-to-end customer usability remain acceptance work.
- The existing large frontend bundle warning remains. This slice adds no measured p95, due-lag, throughput, tenant-capacity or cost claim.
- Quiet hours/business calendars, full sequence/composer/thread UX, assignment/notifications, and real workflow human-task completion remain later work. The modern interactive landing page remains the explicit L4-07/L5-07 deliverable.
- Permanently invalid/foreign pending-policy receipts still need inspected operator remediation; closing a lead event cannot waive that independent dispatch hold. Legacy held events/runs are inspectable evidence, not automatic replay candidates.
- Optional AI adapters still need broader L3 budgets/provenance/evaluation. Repeated generation after a crash is bounded, not guaranteed free of duplicate provider charges.

## Human QA

1. On an isolated migrated database with the normal worker enabled and developer controls disabled, create a synthetic lead, campaign and wait/send sequence. Enroll at a future time and verify both local timezone presentation and saved UTC start.
2. Pause before it becomes due, restart the normal server, confirm it stays paused, then resume with the current revision. Review the actual rendered recipient/sender/message and confirm approval alone never starts a later step.
3. Observe accepted, uncertain, failed and delivered outcomes through supported sandbox/staging controls. Only exact completed delivery should advance; stop must cancel eligible queued work without rewriting in-flight facts.
4. Receive a question, unclear reply and opt-out. Confirm the old sequence stops, appropriate human-response tasks remain, and opt-out intelligence/restrictions stay intact after retry. Use synthetic evidence to exercise a failed processing stage and inspect the recovery queue.
5. Review retry/close evidence with a second stale view. Confirm a conflict refreshes state, history is retained, remaining budget does not reset and mandatory webhook policy cannot be waived.
6. Inspect scheduled/due/invalid follow-ups. Invalid work must show Needs review, refuse completion and allow cancellation. Repeated terminal decisions should not duplicate audits.
7. Verify owner/viewer permissions, keyboard focus, screen-reader labels, narrow/mobile layouts, form errors and navigation without developer tools. Record actual operator feedback before closing L1-06.
