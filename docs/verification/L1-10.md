## Contracts changed

Additive migration **0008_operational_controls** introduces durable auth-admission state/buckets and typed workspace_dispatch_controls. The typed controls row replaces the initial settings-JSON proposal before implementation, avoiding a new PostgreSQL 16 JSON feature dependency or duplicate projection.

Owner **GET/PUT /api/dispatch-controls** derives workspace and actor from the session. Updates carry expected_revision, paused, daily_attempt_limit, unresolved_limit and reason; stale edits return 409 and successful edits record one audit. Missing controls show revision 0, unpaused, 100 attempts per UTC day and 2 unresolved slots. Valid owner limits are 1..1000 daily attempts and 1..10 unresolved slots. Malformed stored controls fail closed.

All persisted SEND authorizations, including sandbox/retry attempts, count toward daily usage. DISPATCHING (even expired) and UNCERTAIN attempts consume unresolved slots until exact outcome/evidence resolution. Conservative legacy ambiguity is visible; it cannot be dismissed by changing quota. The same executor-authorized timestamp selects the quota day and stamps the execution. Candidate SQL only improves scheduling; executor admission remains authoritative.

HTTP limits are 16 KiB headers, configured header/request/body timeouts of 10/30/10 seconds, 5-second keep-alive and at most 64 admitted operations per process. Bodies are 16 KiB for auth, 1 MiB ordinary JSON, 5 MiB CSV preview; existing signed SendGrid event/Parse and batch bounds remain. Auth returns 429 for exhausted durable budgets and safe 503 with Retry-After for busy/dependency refusal. This is bounded application admission, not a guarantee of full network-level protection.

Static pages accept GET/HEAD only and reject mutations with 405/connection close. The local test-only worker route accepts empty or small ignored bodies compatibly, but consumes bounded raw input before worker effects. HTTP capacity is released only after both handler and response completion; shutdown stops new work and awaits disconnected handlers before database close.

Provider response contracts add fixed response_issue and a bounded optional reference; known acceptance never claims delivery. Configuration/TLS bounds and migration-specific values are recorded in [deployment](../DEPLOYMENT.md) and [database evidence](L1-10-database.md).

The isolated workflow check used the existing safe E2E environment and selected a fresh loopback port; it verified the target before mutation and stopped only its owned server.

Independent review reproduced and corrected:

1. Quota inspection could read the next UTC day while execution persistence recorded the prior day's authorization. The shared authorization timestamp regression proves an exhausted prior day remains held and a later genuine day may admit.
2. A disconnected readiness request could release its capacity while DB work continued. Real HTTP regression proves replacements receive 503 and cannot create more DB work; liveness remains 200 without DB access.
3. Server socket closure could allow shutdown to close the database beneath that abandoned handler. A real disconnected-handler drain regression proves the DB remains available until work settles.
4. Public static mutations could serve the SPA and leave arbitrary input unread. Declared large/incomplete POST/PUT/PATCH/DELETE input now receives 405 and closes.
5. The local developer worker route omitted body consumption. Declared/chunked oversize and stalls now fail before worker effects; empty/small non-JSON compatibility and session scope remain.
6. CamelCase log fields bypassed sensitive-key matching and a nonstring URL could execute a coercion getter. Nested redaction/getter regressions preserve safe count metadata with no sentinel exposure.

Initial integration exposed obsolete production fixtures missing the newly required secret/origin, a synthetic webhook generator that did not represent IncomingMessage, and a listener assertion counting Node's own end listener. Fixtures were corrected to exercise their original behavior with valid unrelated configuration/real streams; tests were not deleted, weakened or relabeled as successful PostgreSQL proof. The final combined run includes the review regressions.

## Known issues

- No explicitly disposable real PostgreSQL target was provided for this run. Loopback TLS and actual installed pg policy inspection prove client behavior only; multi-process transactions, server-enforced timeouts, deployed TLS/roles, populated upgrade and restore/rollback gates remain open.
- React compiles and bundles, but no browser automation/human walkthrough was performed. Settings conflict/recovery wording, keyboard/mobile/focus and the complete customer journey need direct validation.
- Limits are provisional operational ceilings, not measured capacity, monetary budgets or complete DDoS protection. Proxy/NAT clients share a coarse socket-peer auth bucket. Production proxy/edge, cost/alerting and load evidence are still required.
- Provider stream doubles do not establish a live send/delivery/inbound loop. Already authorized work may finish after a pause; global changes require coordinated process restart.
- Malformed/foreign pending contact-policy evidence and ambiguous legacy executions may need operator remediation. No owner control waives restrictions or invents acceptance.
- Account recovery/access lifecycle, versioned business context, import correction, shared composition, full inbox/follow-up/outcome flow and validated customer value remain later gates. The requested modern landing page is specified in L4-07/L5-07 and is not implemented.

## Human QA

These are required acceptance steps, not completed checks:

1. In isolated staging, prove hostname-verified database TLS, least-privilege runtime versus migration roles, credential rotation, timeout behavior, populated upgrade and a restored copy without resending old actions.
2. Configure the real public origin/reverse proxy. Verify same-origin login/logout, secure cookies, rejected cross-origin mutations, bounded malformed input and useful throttle/retry behavior without unsafe logs.
3. With two owner sessions, pause a workspace while a reviewed action is due; verify no new attempt. Make competing edits, demonstrate stale rejection, retain the draft and load current controls. Test missing permissions and error/loading states with keyboard/mobile access.
4. Exhaust a provisional daily/unresolved limit using authorized sandbox data; demonstrate a visible hold, UTC-day explanation and exact outcome/evidence recovery. Resume must retain original approval, attempt budget and deadline; no blind resend is allowed.
5. Exercise the selected provider's authorized sandbox and operator recovery, then verify alerts, measured backlog/load/cost and shutdown during active work. Record named owners and evidence before closing L1-10 or any customer gate.
