# Workspace customer-data lifecycle

Recorded2026-09-13 before implementation under COMPLETION_PLAN. Root approved the smallest complete customer-data boundary: export and erase workspace customer records, while retaining the workspace/account and minimum suppression continuity. This is not account deletion, immediate backup erasure or a legal-compliance certification. Full account deletion requires a separate stable suppression/tombstone and re-registration contract.

The data-lifecycle owner implements src/modules/data-lifecycle/*, focused tests and evidence. Root owns migration0023, API/factory/config/UI. Database inventory explicitly includes action_executions via scoped actions and breaks only the documented actions/revisions/executions/workflow cycles. Global public-interest/auth-rate/schema/scheduler records are outside tenant export. Workspace and owner identity fields (organization/user IDs, names, email, role, authentication revision and creation time) export and remain after erasure. Password hashes, session rows/bearers, recovery/security internals, provider credential values and protected evaluation datasets/membership are excluded; underlying customer records export independently without revealing protected membership.

WorkspaceDataLifecycleService(db,{now}) implements inspect/export/previewErasure/erase/byRequestKey/history. Scope is organization_id, actual owner actor and INTERNAL session_token. The HTTP boundary never accepts session/actor identity from JSON. Erase requires current_password, request_key, exact current plan_token and confirmation ERASE WORKSPACE CUSTOMER DATA. Use password admission limits and actual current DB/session/password authority. No password-derived request digest is stored. Completed same-key replay returns original evidence even after new data appears; changed intent conflicts.

Preview is a bounded exact inventory with versioned canonical scoped customer-state hash bound to workspace, current actor and authentication revision. It makes no time-expiry claim; any state or access change invalidates it, and password is reconfirmed at erasure. At most50000rows/32MiB scoped source; SQL preflights field bytes before materializing data, including large legacy fields. The encoded JSON response also has a64MiB cap. Schema table and column names must exactly match the explicit82-table release inventory before either export or erasure. Erase checks the exact state under the workspace gate and completes atomically with a completed-only ledger. It refuses active, uncertain or unresolved historical provider attempts (including CLOSED_UNRESOLVED: closing retry permission does not prove the original transport stopped), active or expired PROCESSING event/receipt leases, mandatory PENDING, admitted/unconfirmed AI calls and RUNNING verification checks. Expired leases do not establish that external work stopped. Established recovery or controlled shutdown must reconcile blockers first.

Erasure removes customer/source/derived/feedback/outbound/workflow data in explicit inventoried order, resets provider credentials/routes/verification, and leaves dispatch paused. Retained account/security and workspace identity permit recovery and suppression matching. Existing EMAIL/PHONE restrictions are retained minimally; LEAD-only restrictions first materialize current exact contacts. Retained rows discard original source/freeform references, detach lead/actor, use fixed MANUAL source and workspace-erasure identity, and preserve channel/reason/effective time. Do not infer legal permission or clear opt-outs.

Signed webhook insertion must recheck captured route/config against current persisted ownership inside the same gate: an ingress request that authenticated before erasure cannot reinsert old customer data after route reset. Existing exact original provider receipts remain idempotent; old aliases cannot authorize new insertions after erasure. Direct source writes must revalidate scoped current lead after acquiring their gate.

Migration0023 workspace_data_erasures records completed-only request/plan hashes, inventory_version1, bounded per-table erased counts, retained suppression count, completion actor/time; no narrative or deleted customer data. Ledger history is bounded1000 and page50. Export includes current erasure receipt history and retained suppression manifest so the operator can retain authoritative lifecycle evidence independently.

A backup made before erasure cannot know a later erasure occurred. Offline restore rehearsal never starts the application/worker and cannot certify lifecycle currency. Activation requires the operator to reconcile independent authoritative erasure/suppression records before traffic/sends resume. This implementation does not claim atomic database-to-external-storage delivery or blindly replay destructive operations.

Verification must cover exact export scopes/secret and HOLDOUT omissions, indirect rows/cycles, metadata byte bounds, current password/session/replay, stale plan/access, blocked in-flight work, complete atomic deletion/rollback, retained opt-out on reimport, route/callback race, new-data preservation on accepted replay and restore activation limitations. No real customer data is operated on while implementing/testing this contract.


## Portable export and retained data

The JSON bundle exports explicit columns grouped by table, with per-table counts, field omissions and a records digest. JSON-valued database fields retain their recorded serialized representation. It is a customer-data export, not a restorable raw database backup. All organization_settings values, raw webhook/callback/inbound transport payload blobs, arbitrary audit messages/metadata, provider-error strings and private feedback snapshots are omitted; canonical message bodies, source/import/research facts, saved assessments, reviewed copy and customer outcomes export independently. User-authored source fields are exported as recorded and are not advertised as automatically scrubbed of arbitrary sensitive content. References to research content or attachments do not fetch or erase remote/file content; no separate attachment binary store is implemented in this slice.

Account identity, session/security and offline recovery state, minimum suppression rows, the technical high-water clock, a fixed dispatch pause and completed erasure receipts remain. Credentials and route aliases are removed from active settings/history. AI control settings and historical attempt accounting are customer operational records and are erased; this does not cancel or refund remote charges. Customer-data erasure also removes private evaluation datasets and reservations; it does not certify newly collected examples as independently held out. New account/customer data created after an accepted command is preserved by same-key replay. Source references in retained restrictions are replaced by fixed erasure identifiers; minimum normalized exact contacts, channel, restriction reason and earliest effective time remain to prevent renewed outreach.

## Support and retention procedure

1. Export needed customer records and independently retain current erasure/suppression evidence using an authorized storage location and retention policy. The application does not claim external receipt delivery succeeded merely because it returned a download.
2. Reconcile pending contact policy and uncertain provider outcomes. Stop/drain affected workers or invocations through the existing operational procedure when claims remain active; an expired lease alone is insufficient. There is no force-erase switch that clears uncertainty.
3. Review the exact current inventory and exclusions, confirm the current password and explicit workspace-customer-data phrase, and submit one request key. Recover an uncertain response with its read-only request lookup. A fresh command is a new reviewed operation.
4. After completion, account recovery remains available, customer records/configuration are removed from the active database and dispatch stays paused. Independently handle authorized backup/export/log/provider retention; logical deletion does not immediately overwrite SQLite pages, journals, replicas or external media.
5. Before restoring traffic from an older backup, keep the application/worker/outbound off and reconcile independent current erasure and suppression evidence. The isolated restore drill certifies structure/integrity only. It cannot discover later erasures from an old backup or authorize activation.

There is no automatic workspace retention schedule, individual lead hard-delete, complete account deletion, external provider purge or backup purge in this contract. The responsible owner must agree permitted processing, actual retention periods, storage access, support ownership and external-copy handling before pilot/public claims.
